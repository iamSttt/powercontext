# 验证样例：午夜美术馆谜案

## 初始状态

- Dify 已启动，已导入 `app/detective-chatflow.yml` 并绑定模型 MiniMax-M3.1-Flash
- 打开应用对话页，出现开场白（欢迎语 + 4 条推荐问题）
- seekdb 中 `dify` 库已有 Dify 迁移生成的表结构

## 验证对话脚本

### 第 1 轮：询问嫌疑人

**输入**

```
苏明那晚在做什么？
```

**预期**

- 以侦探口吻转述苏明的证词：20:00 接班、一直在前门值班室；22:32 前门警报响起，他跑去查看，发现是只野猫；不会直接说出"停电是人为的""馆长是凶手"等结论
- 末尾有「🔍 你掌握的线索：」列出 1—3 条事实

### 第 2 轮：调查物证

**输入**

```
后门的门禁记录说明了什么？
```

**预期**

- 提到后门门禁 22:38 由**林致远的卡**开启、22:41 手动关闭
- 可提及后门监控自 10 月 20 日起报修（但**不主动**说破报修是馆长审批的，除非追问）

### 第 3 轮：核对时间线矛盾

**输入**

```
林致远说 22:00 就离开了吗？车库记录怎么说？
```

**预期**

- 指出林致远陈述 22:00 离开，但车库记录显示车辆 22:45 才驶离，中间 45 分钟无解释
- 回答仍保持悬念，不直接宣布真凶

### 第 4 轮：指认真凶

**输入**

```
我怀疑是林致远。理由有两个：他说 22:00 离开但车库记录 22:45 才出场；而且后门是他自己的卡在 22:38 刷开的。
```

**预期**

- 判定「推理正确」，完整复盘作案过程：投资巨亏 → 提前报修后门监控（10 月 20 日）→ 停电 5 分钟内用馆长卡从后门运走画布 → 用前门野猫警报引开唯一保安 → 22:45 驾车离开
- 说明苏明与顾青无罪

### 第 5 轮：错误指认（可选）

**输入**

```
我觉得是顾青，因为她能进修复室。
```

**预期**

- 不直接揭晓答案，指出证据链漏洞（顾青工作记录连续、车辆未移动、是她提供了识别标签与画布特征等关键信息），提示继续调查

## 技术结合证据

1. **Dify 承担核心流程**：对话记录显示 Chatflow 每次执行「开始 → 侦探主持人（LLM）→ 回答」；开场白、推荐问题、多轮记忆均生效
2. **seekdb 实际写入**（在宿主机执行）：

```bash
docker exec seekdb mysql -h127.0.0.1 -P2881 -uroot dify -e "SHOW TABLES;" | head
docker exec seekdb mysql -h127.0.0.1 -P2881 -uroot dify -e "SELECT id, name, mode FROM apps;"
docker exec seekdb mysql -h127.0.0.1 -P2881 -uroot dify -e "SELECT role, LEFT(answer,80) AS answer FROM messages ORDER BY created_at DESC LIMIT 3;"
```

预期：能看到 `apps` 表中存在「午夜美术馆谜案」，`messages` 表中有本次验证对话的消息记录。

3. **MiniMax 调用**：每轮回答由 MiniMax-M3.1-Flash 生成；可在 Dify 应用日志中查看 token 消耗

## 重置方法

- 重新开始游戏：对话页右上角「新对话」
- 完全重置：删除 Dify 应用后重新导入 DSL；或删除 seekdb 中的 `dify` 库并重启 Dify 容器重建（会清空全部数据）
